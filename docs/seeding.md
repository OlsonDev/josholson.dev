# Seeding

Status: partly built (the layer parser with typed values, the tree, the lock, `seeds:migrate` (which moves the layers forward when the lock is behind, and otherwise checks them), applying a layer's rows, the schema and layer templates, test and dev databases, sequence positioning, and the commands `seeds:bake`, `seed`, `seed:test`, `seed:clean`, `seeds:export`, and `seeds:check`; moving layers from a git base and `seeds:accept` are not). Seeds are dev and test data; reference data lives in migrations.

## Goals

- Pick a seed by name (`bun run seed minimal`) and get a database that has only the data the test needs.
- Keep the number of seeds small and self-describing; avoid inserting data that does not affect assertions.
- Keep seeds valid as migrations change, without hand-editing every file.
- Seed a database, use the app, then export the changes back out as a seed.

## Layers

- The root layer is `minimal` (`seeds/minimal.yaml`): the three tags Database, Language, and Tool, colored `indigo-200`, `emerald-200`, and `amber-200`. `more-tags` extends it with the other 19 tag kinds, each a different family at weight 200, in the `1001..` block, and renames Language to Programming Language by upserting its row (`tag_id: 2`) with only the new `name` and `slug`, so it keeps its color: the layer chain's merge at work.
- Seeds form a **tree** of layers; each layer has a parent (`extends`) and stores only its delta: inserts, updates, and deletes per table, keyed by primary key. Format: YAML ([ADR 0014](adr/0014-hierarchical-seed-layers-in-yaml.md)).
- Each layer has a `description`. `seed list` prints the tree with per-table row counts so nobody has to read a layer to know what is in it.
- Tests needing something extra insert it themselves through a factory, so the relevant data is visible in the test.

## Layer file format

One file per layer in `JoshOlson.Database/seeds/`. The layer's name is the file name without `.yaml` (lower-kebab-case, at most 40 characters, because it ends up in database names). Unknown keys are an error.

```yaml
description: What this layer adds, in a sentence
extends: parent-layer        # omit for a root layer
tables:
  foo.bar:                   # schema.table
    insert:                  # new rows: every column that is not generated from an expression
      - { bar_id: 1001, name: baz, qux: ~ }
    update:                  # rows an earlier layer gives: the key, and only the columns that change
      - { bar_id: 1, name: quux }
    delete:
      - { bar_id: 2 }        # primary key columns only
```

- **An `insert` is a new row and names every column**, except those generated from an expression, a NULL one as `~`. Nothing is left to a column default, which a later migration could change under the seed, and a time is always an offset someone chose (`0s`, or `4s` to put a record after another so the UI does not read out of order), never whatever `now()` gave while the layer was applied. The key must not be a row an earlier layer (or the same layer) already gives: two layers that both claim an ID are an error, not an overwrite, and the key of an identity column must be inside the block of the layer's depth (see IDs).
- **An `update` changes a row an earlier layer gives**, and names the key and only the columns that change, so a diff that fixes one value is one value. Its key must exist, and it must change at least one column. A key never changes: delete the row and insert it again.
- **A `delete` removes a row** an earlier layer gives. In a layer, a table's deletes apply first, then its inserts, then its updates, so a row can be replaced by deleting and inserting it.
- When a migration adds a column, every insert of every layer has to name it. `seeds:migrate` is what does that: it builds the database at the locked version, applies the layers, runs the migration, and exports each layer again, so the new column comes out in every insert, and the diff in the layer files is a record of what the migration did to the seed data. Until it does, the layer check reports each insert that leaves the column out.

- A value's type is its column's type, from `schema.lock.yaml` ([ADR 0035, typed values and relative times](adr/0035-typed-seed-values-and-relative-times.md)). A plain `~`, `null`, or empty value is `NULL`; quoted (`"null"`) it is the string. `jsonb` is native YAML, arrays are sequences, composites are mappings.
- A `timestamptz` column is relative by default: its values are signed offsets from the database's anchor (the time it was hydrated), so seeds never hold real dates. An offset is written like `-3d 4h 12m 0.0123s`: lowercase `d`, `h`, `m`, `s`, zero units left out, `0s` for zero, one `-` for the whole duration, exact to the microsecond. A column opts out with `@seed absolute` in its `COMMENT ON COLUMN`. The choice is per column, never per value.
- Formats by type: `boolean` is `true` or `false`; integers are digits with an optional sign, inside the type's range; a `decimal(p, s)` column refuses more digits than it holds, since Postgres would round them; an absolute `timestamptz` is a UTC instant (`2026-01-02T03:04:05.123456Z`), never finer than a microsecond; `bytea` is `\x` and hex digits, as Postgres prints it; `inet` is an address, with `/bits` for a network (a prefix as long as the address, `/32` or `/128`, is one host, which Postgres does not tell from the bare address, so it is left off); inside `jsonb`, a plain `true`, `false`, `null`, and number are those JSON values and anything quoted is a string. A `jsonb` value has one text, `JsonCanonical`: compact, each object's keys in the order Postgres stores them (shorter keys first, then bytewise) and the last of a repeated key kept, so a value read from a file equals the same value read back from the database whatever order the file wrote its keys in.
- Parsing reads each value as its column's type from the lock (`mise run seeds:list` needs the lock to exist once there is a layer). A file that is not the shape above fails at the first fault. Past that, every problem with its tables and values is collected and reported together: an unknown table or column, a value that is not its column's type, a NULL in a `NOT NULL` column, a missing key column, an insert that leaves a column out, an update that changes nothing, a delete that holds more than the key, and a column generated from an expression. Whether an insert's key is new and an update's is not is found when the chain is merged (`LayerMerger`), and whether an insert's ID is in its block when the layers are loaded (`LayerLoader`).
- Parsing and the tree (duplicate names, a missing parent, and cycles are errors) are `JoshOlson.Database/Layers`. `mise run seeds:list` prints the tree.
- **A table can opt out of seeding.** `COMMENT ON TABLE auth.session IS '@seed ignore'` says its rows are runtime data (sessions, credentials, the user-agent cache), not seed data. The lock records it as `seed: ignore`, and then:
  - a layer cannot name the table (a parse error naming it);
  - a database built from a layer leaves that table's identity sequences where they were, outside the ID blocks;
  - `SeedStateReader` and so an export skip it, so using the app and exporting does not put sessions into a layer.
  - The directive is for a table and nothing else: `@seed ignore` on a column is a problem, like any `@seed` word the tool does not know (a typo would otherwise leave a runtime table in every export). A column the app writes inside a table that is seed data is a different case, and is not handled yet.
  - The tables marked today are `auth.session`, `auth.enrollment_token`, and `http.user_agent`: what signing in, minting a token, and browsing leave behind. The user, their email, and their passkeys (`auth.user`, `auth.user_email`, `auth.passkey`) are seed data, so an end-to-end test can start already signed up and begin by logging in. Like `@seed absolute`, it is metadata the tool reads, not an explanatory comment, so it is not one of the comments `sql.md` says migrations do not have yet.

## IDs

- Layers carry explicit IDs, inserted with `OVERRIDING SYSTEM VALUE`, in blocks of 1000 per depth, where a layer's depth is how many parents it has: the root `minimal` uses `1..1000`, its children `1001..2000`, their children `2001..3000`, and so on (`IdBlocks`: depth × 1000 + 1 up to (depth + 1) × 1000, the same for every depth). Siblings share a block because they never coexist ([ADR 0015](adr/0015-seed-id-blocks-and-sequence-cursor.md)). A block is for the rows a layer adds; an upsert of an ancestor's row keeps its ID (`more-tags` upserts `tag_id: 2`).
- While layers apply for a migration, each identity sequence is positioned by the root's rows only, so a migration that generates IDs produces the same IDs in a parent and in its children.
- A database built from a layer for use (the dev database, a test's, a template) hands out IDs from the **next** depth's block: every identity sequence, in every table, is set so that the next generated ID is the first of that block, or past the chain's largest ID if that is higher. So `seed minimal` gives a new tag `1001`, `seed more-tags` gives `2001`, and a table no layer has rows in starts at the same place. What you create in the app is then already where an exported child layer keeps its new rows, and cannot collide with a row of any layer at the same depth or above.

## Build and run

🚧 Built so far (`JoshOlson.Database/Seeding`): `LayerMerger` folds a chain of layers, root first, into the rows they come to (in each layer a table's deletes apply first, then its inserts, then its updates; every problem is reported together, including an insert of a key that is already there and an update or delete of one that is not), and `SeedSql` turns those rows into typed `INSERT` statements in foreign-key order, with `OVERRIDING SYSTEM VALUE` for identity columns and relative times worked out against a given anchor (every row names every column, so no `DEFAULT` is ever written, and a row that leaves one out is refused). `SeedApplier` runs a layer's chain (merge, build, execute in order) inside a transaction the caller owns, and names the table when an insert fails. Its tests, like the rest of the seed tool's, connect as the owner and roll back. `SchemaTemplate` (`JoshOlson.Database/Baking`) builds the schema template: it creates a database named `seed_schema_v<N>_<hash>` for the newest migration `N` (the hash covers the versioned migrations up to it, every repeatable one, and both scripts), applies the versioned migrations with Waypoint in the `tools` container and then each repeatable one the same way (see the version templates under Migrating seeds), runs `provisioning/api_role.sql` through `psql` in the `postgres` container, then `Baking/seed_schema.sql`, which creates the `seed` schema with `seed.hydration` (one row, the anchor, filled when a layer is applied; it comes after the API role's script so the role is granted nothing in it), and sets `ALLOW_CONNECTIONS false`. Both scripts are in the hash. It builds under a `_building` name and renames at the end, so a bake that dies halfway leaves no template that looks finished, and it does nothing when the template for the current files exists. Every database the tool makes starts with `seed_` (`SeedDatabaseNames`).

Layer templates, test databases, and the commands (`Baking/`, run through `JoshOlson.Seed`, the command line; each takes a connection to the `postgres` database, since Postgres cannot drop or clone a database someone is connected to):

- A **layer template** (`LayerTemplate`) is `seed_layer_<hash>`, where the hash covers the schema template's name and the source of every layer in the chain, so a change to any file the layer depends on gives a new name and a change to a sibling does not. It is a clone of the *schema* template (`ServerDatabases.CloneAsync`, which retries error 55006, the source still in use) with the layer's whole chain applied (`SeedHydrator`), not of the parent's template plus the layer's delta: the rows are the same, and a delta would need an `UPDATE` and `DELETE` writer beside the `INSERT` one. It is built under a `_building` name, renamed at the end, and refuses connections, like the schema template (`ServerDatabases.EnsureTemplateAsync`).

`ServerDatabases` (`Baking/`) is the one place that creates, clones, drops, closes, renames, lists, and looks for databases on the server; no other class writes `CREATE DATABASE`, `DROP DATABASE`, or `ALTER DATABASE`. A name reaches it only through `SeedDatabaseNames`, which checks it before it is quoted into SQL.
- **Hydrating** (`SeedHydrator`) applies the chain in one transaction, records the anchor in `seed.hydration` (the bake time, cut to a microsecond, which is also the clock a test starts at) beside the layer's name and an `editing` flag (see Export), and then positions the sequences. `SequencePositioner` has both rules from ADR 0015 (seed ID blocks): `ChainAsync` moves every identity sequence to the start of the next depth's block (`IdBlocks`), or past the largest ID its table has in the whole chain if that is higher, which is what a database built for use gets (a database built for editing the layer itself, `seed <layer> --edit`, gets the start of the layer's own block instead), and `RootAsync` moves the sequences of the tables the root layer has rows in to the largest ID there, which `seeds:migrate` will use when it replays migrations over layers. A sequence never moves backwards.
- `mise run seeds:bake` builds the schema template and then every layer's template, parent first; templates that are current are left alone. `mise run seed:test <id> <layer>` clones the layer's template into `seed_test_<id>` (the id is lowercase letters and digits, at most 40) and prints its name. `mise run seed <layer>` drops the dev database (`POSTGRES_DB`, never a server database) and makes it again from the schema template with the chain applied and the anchor set to now, so its relative times are current; everything in it is lost. `mise run seed:clean` drops every `seed_` database the current migrations and layers do not name (old templates, test databases, builds that died halfway), and `seed:clean --all` the current templates as well.
- The tests bake the real layers and share the real templates, so classes that build or clone one run one after another (`TemplateCollection`); the template test uses a copy of the migrations with one extra file to get a name of its own.

- `bake` (once called `compile-seeds`) resolves layers to SQL, orders inserts by foreign key, validates them against the current schema in a scratch database, and saves each layer's template with its typed fixtures.
- Databases are cloned with `CREATE DATABASE ... TEMPLATE` on the one Postgres server ([ADR 0013](adr/0013-single-postgres-server-with-template-databases.md)): a template per schema version, a template per layer named by a hash of the migrations and layer source, and a clone per test ([ADR 0033, a scoped database per test](adr/0033-scoped-databases-per-test.md)). The tool is `JoshOlson.Database`.
- The tool only touches databases with its own prefix plus the configured app database, uses a role with `CREATEDB` and no superuser, and refuses to run unless the host is allowlisted (localhost).

## Migrating seeds

`JoshOlson.Database/migrations/schema.lock.yaml` is generated, never edited by hand. It records a checksum per versioned migration the seeds were migrated against (the newest is the version the seeds were last migrated to; there is no separate `version` line, so the two cannot disagree), and the schema those migrations produce (each column's type, default, comment, and seed policy, the domains with their checks, the keys and constraints, the indexes, and the schema comments; `docs/schema` is rendered from it as well) ([ADR 0034, lock file and branch-safe migration](adr/0034-seed-lock-file-and-branch-safe-migration.md)). `seeds:migrate`, parent first, for each node:

1. Build the database at the locked version (migrations 1 through N, a cached template) and apply the chain root to node.
2. Apply the next migration. The result is the node's migrated full state.
3. Export the node's layer as the diff against its migrated parent's full state.
4. Verify that the parent state plus the new layer equals the migrated full state. Write nothing, for any layer, if any layer fails.

Only layers whose diff changed are rewritten, and a per-layer summary is printed for review. Additive migrations need no seed work.

🚧 Step 1's database is a schema template at an older version (`SchemaTemplate.EnsureAsync(owner, version)`; the same class builds the newest one, which is what everything else uses). It is built in four steps whatever the version: (1) the versioned migrations up to it, by Waypoint from a directory of their own in the `tools` container (`ComposeTools.MigrateAsync` with files: sent as base64 so the bytes are exact, written, migrated, and removed by one script in one round trip, read through `WAYPOINT_LOCATIONS`; `--target` is no use, because it still runs the repeatable migrations); (2) each repeatable migration on its own, in name order, by Waypoint with `--transaction`, so its history records every one that applied (with its checksum, as for a database migrated by hand) and a failed one leaves no row; (3) the API role's provisioning and (4) the `seed` schema, one `psql` session. Commands go to the containers with `podman exec`, found once by their compose labels, not `podman compose exec`, which re-reads the project on every call and takes twice as long; each round trip costs about a fifth of a second, so a step that is several commands runs as one script in the container where it can. Repeatables are written for the newest schema, so at an older version one can fail for want of a table or column: it is skipped and noted (`SchemaTemplate.SkippedAsync`, kept in the template's database comment, which can be read without connecting to a template) instead of failing the build, and it runs when the database goes on to the newest version (repeatables are safe to run again). At the newest version a failure is an error. The name is `seed_schema_v<N>_<hash>`, the hash covering the version, the versioned migrations up to it, every repeatable, and both scripts, so the same name always has the same skips. Every template provisions the API role, so building one needs `POSTGRES_API_PASSWORD`. `mise run tools:up` rebuilds the image when `tools/` changes and recreates the container when it is running an older image.

🚧 Built so far: the lock, and moving layers forward from the working tree. `mise run seeds:migrate` (`JoshOlson.Database/Migrate`) checks the lock against the migrations on disk (the same check `seeds:check` runs), builds (or finds) the schema template for the newest migration, checks that Waypoint's history in it matches the files, reads its catalog, and writes the lock at the newest migration, keeping any accepted checksums. The dev database plays no part: it can be in any state, or missing, and there is no `waypoint migrate` to run first. It reports every problem together and writes nothing if there is one.

When the lock is behind the migrations on disk and there are layers, `LayerMover` does steps 1 to 4 on the layers in the working tree, read against the old lock's schema. Each layer, parent first, goes into a clone of the template at the locked version (`SeedHydrator.HydrateForMigrationAsync`), and the migrations after it run on the clone (`SchemaTemplate.MigrateToNewestAsync`, repeatable ones included), so the database is the layer's full state at the newest version. Each layer is then exported again as the difference between its state and its parent's (a root's: the newest template's), which is how a new `NOT NULL` column comes out in every insert and a data migration changes the layer. Every new layer is checked in memory (its parent's state with the layer applied is its own, its inserts keep to their ID blocks, its text reads back as itself) and then applied to a clone of the newest template, where foreign keys, unique values, and checks are enforced. Only the layers whose text changed are rewritten, and the files go first and the lock last, so an interrupted run leaves a lock that still says the old version and `seeds:check` flags the layers.

Two choices follow from reference data being in repeatable migrations, which are written for the newest schema. At the locked version a repeatable may not apply (the template notes which: `SchemaTemplate.SkippedAsync`), so a layer row can point at reference data that is not there yet; foreign keys are therefore not enforced while the rows go in at the old version, and are enforced when the layer is built at the newest. A failure there names the layer and the repeatable that was skipped. And a migration has to give the same result for the same rows every time, because each layer is migrated in a database of its own and a child is compared with its parent's: a default of `now()` on a new column would make a child appear to update every row it inherits.

When the lock is not behind (or there is no lock, or `--relock`), the layers are checked instead: each is read against the schema the new lock describes and built into a template (`SeedTool.CheckAsync`), every layer that fails is reported, children of a failed layer skipped, and the lock is written only when all of them apply. What none of this catches is a migration that changes what a column means and leaves the layer valid, which tests built from the layer show.

**Whose a layer file is.** The lock's `layers` section records the SHA-256 of each layer file `seeds:migrate` wrote (`LockedLayer`, `LayerChecksum`). A file that still hashes to its recorded value is the tool's own (`GeneratedLayers`), and the tool may write it again. Any other file (one you wrote with `seeds:export`, or edited since) is yours: it is moved forward with the rest, but is not recorded, so it stays yours, and the tool never replaces it with what it generated. A lock with no `layers` section (one from before they were recorded) takes every layer to be the tool's, which is how the first run records them, and `layers: {}` says there are layers and none is. This is what lets a layer re-derived from a base (see below) keep what you added.

Not built yet: re-deriving a layer from a git base when the lock is already at the newest version (re-iterating an unmerged migration), and `seeds:accept`.

Until the first deploy, migrations may be rewritten (`sql.md`), which leaves the lock's checksums stale and Waypoint refusing the changed file. Two commands cover that: `mise run seeds:relock` writes the lock afresh from the schema the migrations produce, ignoring the old lock's version and checksums (it still checks that the template's history matches the files, and checks the layers the same way), and `mise run db:reset`, for the dev database only, drops it and rebuilds it from the migrations (everything in it is lost), which is what Waypoint needs once a file it applied has changed. Both are retired at the first deploy, when migrations become immutable.

`mise run seeds:check` changes nothing and exits 1 with every problem listed, so a hook or CI can run it. It checks the lock (`SeedMigrator.CheckLockAsync`: it exists, describes the migrations on disk, and is at the newest one, so a migration newer than the seeds is a problem) and then every layer (`SeedTool.CheckFilesAsync`): the file is exactly the canonical text `LayerWriter` writes, it builds into a template, and it gives itself back (a clone of its template is read with `SeedStateReader` and diffed against its parent's template, which must give the layer's own text again). A layer that fails is named with its first differing line or Postgres's message, and the layers below it are skipped.

If two branches claim the same migration number, `seeds:check` names the first migration that differs from the lock. Rename yours to the next number, take the main branch's `seeds/` and `migrations/schema.lock.yaml` wholesale, and rerun `seeds:migrate`.

If you only edit an already-applied migration's comment or whitespace, its checksum changes. `seeds:accept <version>` rebuilds with the edited file and, only if the catalog still equals the lock and every layer still exports to its own file, records the new checksum as accepted. If either differs, the edit changes something the seeds see, so add a new migration instead. The checksum is the SHA-256 of the raw file bytes; nothing is normalized.

## Export

```
mise run seeds:export --name <name> --description "What it adds"
```

`seed export` diffs a database (the dev database, or `--database <name>`) against the parent's template, which is the layer the database was built from (`seed.hydration` records it beside the anchor), checks the result, and writes `seeds/<name>.yaml`. A database that records no layer (made by the migrations alone) makes a root layer, diffed against the schema template, with relative times measured from now. There is no `--parent` or `--root`: the database says which. `--overwrite` replaces a layer of that name when no other layer extends it. Primary keys are required on every table. The tables it found rows in are listed as it writes, so a row that should not be there is not a surprise in the diff.

- **What the database says decides the rest.** `seed.hydration` records the layer the database was built from and whether it was built for `editing` it. There is no `--parent` or `--root`:
  - Built from a layer (`seed minimal`): the export is a child of it, and `--name` and `--description` are required. New rows took IDs from the next depth's block, so they are in the child's block (`1001..` for a child of a root).
  - Built for editing (`seed parent --edit`, or exported before): with no `--name` (or the recorded layer's own), the layer is replaced in place, its description kept, and its baseline is its parent's template. Any other `--name` makes a sibling that extends the same parent, and needs `--description`. The sequences stay in the layer's own block, so what is made exports into it.
  - No `seed.hydration` row (made by the migrations alone): a root, with relative times measured from now (so history is negative and a scheduled time positive).
  - After the file is written the database is recorded as `layer = <exported name>, editing = true`. The next export replaces that layer, and `seed <layer>` (a rebuild, which loses nothing just exported) starts a child of it. The sequences need no move: the layer's rows took IDs from its own block already.
  - Replacing a layer that others extend is allowed while they still apply. Every layer below it is merged again against the new version (an `update` or `delete` of a row the parent no longer has, or an `insert` of a key it now has, is a problem) and its inserts are checked against their blocks. The merge is in memory, so each of those layers, and the new one, is then also applied to a clone of the schema template, where a foreign key to a row that is gone, a duplicate of a unique value, or a failed check shows. The export names the layers that would break and writes nothing. A descendant's inherited values may change when its parent does (a column its `update` does not name, a row the parent added or dropped); that is not checked, because a test built from the descendant shows when it matters.
- `SeedStateReader` reads every table of a database except those marked `@seed ignore` into the same `SeedState` a chain of layers merges to, typed through the lock: one repeatable-read transaction, with the session pinned to UTC and ISO dates, each cell as the text Postgres prints for it and then read as its column's type. A relative `timestamptz` is the signed whole microseconds from the anchor in `seed.hydration`, an absolute one the UTC instant, and a column generated from an expression is left out (a layer cannot give it a value). A database with no anchor was not built by the seed tool and is refused, unless the caller gives an anchor to measure from (an export of such a database does).
- `StateDiffer` compares two such states by primary key and `LayerWriter` writes the result as the layer's one canonical text. A template refuses connections, so `SeedTool.ExportAsync` reads a scratch clone of the parent's template (or the schema template's) and drops it. Before it returns, the export checks that the new inserts' IDs are in their depth's block and that the baseline with the layer applied gives back exactly the rows read from the database, and that the text reads back as the same layer; a bug in any step fails the export instead of writing a layer that is wrong. Exporting a database that was built from a layer, as a copy, reproduces that layer's file byte for byte apart from the description, which is how it is tested.
- A fresh database is not empty. The repeatable migrations put reference data in every one (mime types and the like), so the baseline an export is measured from is a template that already has it: the parent's template, or for a root the schema template. Reference data therefore never lands in a layer, which is what keeps it in migrations and out of seeds.

- The diff is as small as it can be: a row that is new is an insert of every column (so a relative time is always written, as the offset the database holds, and no default is relied on); a row that exists in the parent's state and changed is an update of its key and only the columns that changed (the merge rebuilds the full row); a row that is gone is a delete of its key. A row that did not change is left out.
- The flow it is built for: `seed minimal`, use the app, `seeds:export --name more-but-different-tags`. The new rows came from sequences that start at the next depth's block, so they already carry IDs `1001..` (see IDs above). The export refuses a new row whose ID is outside its layer's block (`IdBlocks.Contains`), naming the table and the ID, because a row at an ancestor's depth could collide with one the ancestor adds later. The same check runs on every layer file as it is loaded.

- Relative columns are exported as offsets from the anchor stored in the database being exported (`seed.hydration`), never from `now()`, in exact microseconds. Output is canonical (sorted by primary key, columns in catalog order), so unchanged rows give identical text and `seeds:check` can require a byte-for-byte round trip.
- Tests on this assert at one-microsecond increments ([ADR 0035, typed values and relative times](adr/0035-typed-seed-values-and-relative-times.md)).
- `mise run seed <layer>` for the dev database applies the layer with the anchor set to now, so every relative column is current. Test clones keep the anchor they were baked with, which is also their `FakeClock` start.
- Fixtures for tests come from reading the baked template back with real types, not from the YAML.

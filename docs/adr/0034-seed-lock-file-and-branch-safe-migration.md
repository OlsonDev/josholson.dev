# ADR 0034: Seed lock file and branch-safe migration

- Status: Proposed
- Date: 2026-11-03

## Context

Seed YAML is written against one version of the schema. When a migration lands, the seeds must move with it, and the tool has to cope with two things a bare version number cannot:

- **Branches.** Two developers can each claim migration 43. One merges first, the other renames theirs to 44, and a seed stamped "43" now means different things on the two branches.
- **A migration that fails on some seeds** while it is still being perfected must not leave the seeds half converted.

SQL Server projects solved the first half with a snapshot script at the last released migration. Here, [ADR 0033 (a scoped database per test)](0033-scoped-databases-per-test.md) already caches a template per hash of the migrations, so a database at any earlier version is cheap to rebuild.

## Decision

- **`migrations/schema.lock.yaml` is generated, never hand-edited.** It sits with the migrations because it describes both: the migrations it checksums and the schema the seeds are written against. It records a checksum for each versioned migration the seeds were migrated against (the newest of them is the version the seeds were last migrated to: there is no separate `version` line, so it cannot disagree with the list and is one less line two branches conflict over), and the schema those migrations produce, so it is the one artifact everything about the schema is derived from (see below). Repeatable (`R__`) migrations are left out of the checksums, since reference data changes often and is applied at head.
- **The lock is the schema snapshot.** One catalog reader in `JoshOlson.Database` reads the schema into a model, and the lock is that model's canonical serialization. It grows in two stages:
  - First what the seed tool needs: per column its type, nullability (`nullable` is the effective value, false also when the column's domain is `NOT NULL`; `declared_nullable: true` is written only for a nullable column of such a domain, so flipping a domain's `NOT NULL` shows in the lock diff as `nullable` changing on every column it affects), `generated_as` (`identity-always`, `identity-by-default`, `expression-stored`, `expression-virtual`, named for the `GENERATED` clause), and the seed policy (see [ADR 0035, typed values and relative times](0035-typed-seed-values-and-relative-times.md)); per table the primary key as a list of column names in key order, and the foreign keys, which order the inserts; and a top-level `domains` map, each with the type it is built on and its `CHECK` constraints, so a column says only the domain's name and `seeds:accept` can see a rule change.
  - Then what the schema docs need: defaults, comments, unique and table check constraints, index definitions, and schema comments. Nothing is read from the lock that the catalog does not say, and `seeds:check` fails if the two differ.
- **A type is written in its cleanest `CREATE TABLE` spelling:** `timestamptz`, `decimal(9, 6)`, `smallint[]`, or a domain's `schema.name` (`foo.bar[]` for an array of it). The catalog reader makes Postgres print this form (`timestamp with time zone` to `timestamptz`, `numeric(9,6)` to `decimal(9, 6)`), so the C# side parses one spelling, names the supported types by their `SeedType` member, and refuses anything else. A domain may be built on a base type, an array, or another domain; one array dimension only.
- **`docs/schema` is generated from the lock, not from a database.** `schema:doc` renders the pages from the lock, so it needs no running database, and `schema:check` (render the lock and compare) needs none either. This replaces the live-catalog reader in `scripts/schema-docs.cs` described in [ADR 0021, generated schema docs](0021-generated-schema-docs.md). The docs therefore follow the lock's version: while a migration is being perfected they show the previous one until `seeds:migrate` restamps the lock. A pull request cannot merge with the lock older than the newest migration: an additive migration only needs a restamp, which changes no layer.
- **`seeds:migrate`** moves every layer to the next migration, all or nothing:
  1. For each layer, parent first, build the template at the locked version (migrations 1 through N, cached by checksum), apply the layer's chain, then apply migration N+1.
  2. Export the layer as a diff against its migrated parent, and verify that the parent's state plus the layer equals the migrated state.
  3. Write the new layers and lock only if every layer succeeded. Otherwise write nothing, report each failing layer with the Postgres error, and drop the scratch databases (an option keeps them for debugging).
- **A mismatch names the migration.** If the lock's checksums differ from the migrations on disk, the tool reports the first migration that differs ("the seeds' 43 is not your 43") and prints the fix instead of failing generically. The checksum is the SHA-256 of the file's raw bytes (the repository keeps every file LF-terminated UTF-8), so there is no normalization to get wrong.
- **A benign edit to an applied migration is accepted by effect, not ignored by syntax.** Editing a comment or whitespace in migration 42 changes its checksum, and the lock then reports it as changed. `seeds:accept 42` rebuilds the database at the locked version with the edited file, and records the new checksum under that migration's `accepted_checksums` list only if two things still hold: the catalog equals the lock's tables and columns, and every layer exports to its own file, byte for byte. If either differs, the edit is not benign for the seeds and the tool refuses; the fix is a new migration. The old checksum stays valid, so a branch that still has the old text still matches. The lock records the acceptance, so a reviewer sees it in the pull request.
- **Resolving a branch conflict means regenerating, not merging.** Rename the migration to the next free number, take the main branch's `seeds/` and `migrations/schema.lock.yaml` wholesale, and rerun `seeds:migrate`. Because export is deterministic, the diff is exactly what the migration changed.
- **`seeds:check`** fails if the lock differs from the catalog of a database built at the locked version, or if any layer does not export back to its own file (drift, see ADR 0035, typed values and relative times).
- The tool takes its paths and schema exclusions from configuration, not constants, so it can move to another project.

## Alternatives considered

- **A bare version number** (the earlier `.schema-version` file in `seeding.md`): cannot tell two branches' 43 apart.
- **A snapshot script at the released version**: a second artifact to keep in step with the migrations. Templates keyed by checksum rebuild any version from the migrations alone.
- **Hashing with whitespace and comments removed:** whitespace can be significant inside a string literal or a function body, and a comment may be part of a stored definition. Telling them apart needs a full SQL parser.
- **Hashing a parsed form of the SQL:** the same parser, and a hash that would hide changes the seeds do care about.
- **Hand-merging seeds when branches meet:** error-prone, and the diff of a regenerated export is smaller and exact.

## Consequences

- A migration that changes a column's type or policy needs no seed edits by hand: `seeds:migrate` rewrites the lock and the values together.
- The lock can say an older version than the newest migration on disk: that is the state while migration N+1 is being perfected. The checksums skip the lock itself, and Waypoint ignores a `.yaml` file among the migrations (checked with `waypoint info`).
- The tool writes into a folder that is otherwise hand-written and append-only, so a change to the lock in a pull request is always the tool's doing and is reviewed as such.
- Editing an old versioned migration changes its checksum and invalidates the lock until the edit is accepted or reverted. Waypoint's own history table holds a checksum as well, so a database that already applied the old text needs Waypoint's own repair step. The lock's contract is about the seeds: an accepted edit means every seed is unaffected, not that the migration is unchanged. A function body that no seed depends on can change behavior under an accepted edit.
- The lock model (`SchemaLock`, its checksums, and the check) is built and tested. The first stage of the schema snapshot is in it too: per column the type, `generated_as` and seed policy, per domain the type and checks, and per table the primary key and foreign keys, with `InsertOrder` and `DeleteOrder` derived from the keys (an initially deferred key does not constrain the order, and a loop with no deferred key is an error naming the tables). The catalog reader (`SchemaCatalog`) produces that first stage from a database: Postgres prints the types in the lock's spelling, and the queries fill the model types directly (types stay text; a child's parent oid comes back beside it, not on it). A column of a type with no seed type, and a bad `@seed` comment, are problems named by table and column, all reported together. And `COMMENT ON COLUMN ... @seed absolute` sets a `timestamptz` column's policy. The second stage is in too: schema, table, column, and domain comments; column defaults and generation expressions; domain defaults and `NOT NULL`; the primary key's name, unique constraints, table checks, and the indexes that back no constraint, each with its definition as the catalog prints it, kept as text. `scripts/schema-docs.cs` renders `docs/schema` from the reader's model, which is the model the lock serializes, so it matches the lock's content. `seeds:migrate` generates the lock (`SeedMigrator`): it checks the lock against the migrations on disk, checks the dev database has applied exactly those migrations (the versions and file names in Waypoint's history table, since Waypoint's own checksum is not a SHA-256), reads the catalog, and writes the lock atomically at the newest migration, keeping accepted checksums. Every problem is reported together and nothing is written if there is one. Moving the layers is not built, so it refuses while any layer exists. What remains is moving layers, `seeds:accept` and `seeds:check`, and then rendering from the lock file instead of the live database.
- The lock is large for a generated file, but a schema change shows up in it in review, next to the migration that caused it.
- The editor opens the lock and the seed layers read-only by default (`files.readonlyInclude`), so a hand edit is a deliberate step.
- A repeatable migration that removes a reference row a seed points at is not caught by the stamp. Bake fails on the foreign key instead.
- Waypoint's `--target` builds the old-version database, so the tool needs the dev `tools` container ([ADR 0020, Waypoint in a dev container](0020-waypoint-in-a-dev-tools-container.md)).

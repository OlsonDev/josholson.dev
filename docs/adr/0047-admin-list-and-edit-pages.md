# ADR 0047: List-and-edit pages in the admin

- Status: Accepted
- Date: 2026-11-19

## Context

Tags are the first of many admin pages that list something and edit one item of it (résumés, skills, projects, posts). Each needs the same things: a form that knows when it changed and what is wrong with each field, a way to leave it without losing work by accident, a delete that says what it would affect, and a layout where the list and the editor feel like one place. Built once for tags, they would be rebuilt (and drift) for the next page, so the parts are made generic now and tags is their first user.

## Decision

- **The URL is the state.** `/admin/tags` is the list, `/admin/tags/5` edits a tag, and `/admin/tags/+` makes a new one (`+` and digits are the `paneid` param, `src/params.ts`; anything else is a 404). `ListPane` is the layout of a list route: the list is always drawn, and when the URL is a pane's it slides left (clipped at the content area's edge, which is under the sidebar, or off the screen when the sidebar is collapsed), the pane slides in from the right, and its action bar comes up from the bottom. Closing is the same in reverse. Because the URL decides, the back button, Cancel, and a confirmed discard all play it, and a pane can be opened by its address. The list is `inert` while the pane is open, focus goes to the pane's heading and back to what opened it, and reduced motion fades instead.
- **A list pages by its address.** `?page=2&size=25` (`list-state.ts`; the defaults are left out, so the first page is the plain address), read with `parsePaging`, which clamps a page past the end to the last. The list pages on the client for now, over everything it already loaded, with `Pager` (real links, the rows showing, and the page sizes) in `ListBar` along the bottom and the page's main action, "+ Add tag", at its right edge. Server paging (a total and a page from the API) is for when a list can be thousands or needs server-side search, and does not change the addresses. A pane's address carries the list's query (`/admin/tags/5?page=2`), so the list behind it stays on its page, and Cancel, Save, and Delete return to it.
- **A section of the thing is an address too.** The tag's Details and Used by are `/admin/tags/5` and `/admin/tags/5/used-by`, links (`TabLinks`) and not scripted tabs, so a refresh, back, or a shared link stays on the section. The editor lives in the `[tagId]` layout, so the form and what was typed survive a switch, and `UnsavedGuard` is told that moving between the sections of the same tag is not leaving it.
- **The breadcrumbs say where you are.** A page inside a page gives its own trail after "Admin" (`Crumbs`, read by the header from a context), so a tag being edited is `Admin > Tags > Communication`, with the list as a link at the page it was on: the step back is the crumb next to where you are.
- **Bars are rows.** `ListPane` is a column: the scrolling part, then one bar, the list's own or the pane's. A bar under the scroller, not over it, means a scrollbar stops where the bar begins, and the bars change height (not slide) as one leaves and the other arrives. The scrolling parts keep the room for a scrollbar on both sides (`scrollbar-gutter: stable both-edges`), so content does not move when a section is too short to scroll.
- **The page says which mode it is.** `color-scheme` follows the `dark` class, so the browser draws scrollbars and native controls to match, and scrollbars are thin and take their color from the theme.
- **Form state is one class.** `FormState` (`web/src/lib/admin/form.svelte.ts`, runes) holds the values and what they were loaded as (dirty is a deep comparison), the errors by field (the client's rules, or the API's `fieldErrors`; an error clears when its field is edited), a count for the bar ("Please address the 3 validation errors."), and `focusFirstInvalid`, which picks the topmost `Field` with an error in page order whatever order the errors arrived in. The rules in `validateTag` mirror the API's, so most mistakes show before the round trip and the API still decides last. Pure parts (`sameData`, `firstInvalid`, `countMessages`, `slugify`) are plain modules with unit tests, since Bun cannot run runes outside Svelte.
- **Leaving is guarded.** `UnsavedGuard` holds every in-app way out (links, `goto`, back and forward) while the form is dirty and asks with `UnsavedChangesDialog`. Confirming a back or forward moves through history the same way (`history.go(delta)`), so it leaves no extra entry. Closing the tab or reloading is the browser's own prompt, which cannot have our words.
- **Delete says what it affects.** `ConfirmDelete` is one component for every delete. The API returns `{ blockers, warnings }` (each a list of `{ kind, count }`; ADR 0046 on tags covers its side), the web names each kind (`impactKinds`: words, icon, page, one entry per `DeletionImpactKind`, so a new kind does not compile until it has words), and the dialog shows the wait, the blockers (nothing to confirm), the warnings and the typed confirmation (`delete-<slug>`; none for something trivial), or the confirmation alone. Deleting asks the API again, which refuses with the blockers if something blocked it since, and an item that is already gone counts as deleted.
- **A save can lose to another.** The edit form sends the version it loaded, and on a `409` offers to load the other save (discarding the edit) or to save over it.
- **Tags look the same everywhere.** `Tag` is one chip for the public pages and the admin: the color is the light-mode background, dark mode paints the mirror (`tagColors`), and a description shows in a hover card (the browser's `interestfor`, shipped only in Chromium so far, is the thing to switch to when it is everywhere). The palette is generated twice from Tailwind's theme (`mise web:palette`): TypeScript for the contrast ratios, and CSS custom properties (`--palette-emerald-200`) that a chip paints with, so what the picker measures is what is painted, and no class is built from a color name. They are deliberately not Tailwind theme variables: those are only emitted when a class uses them, and redefining them would change every `bg-emerald-200` on the site.
- **The palette is not about tags.** `src/lib/palette` holds the Tailwind palette (the color names and their mirrors, contrast ratios, the generated values) and `ColorPicker`, and knows nothing of tags: the one tag-specific part, how a chip is painted (`tagStyle`), is in `src/lib/tags`. The picker takes a `preview` snippet, which draws the sample in each row of its contrast table from the row's colors, so the tag editor shows its chip with the name being edited and another page could show whatever it colors.
- **The color picker.** A popover grid of the palette in the weights from the page's own end of the scale (50 to 500 in light mode, 950 to 500 in dark), storing the light-mode name either way. Hovering or focusing a swatch shows, for light and dark, how black or white and the family's own darkest or lightest weights read on it: the WCAG 2 ratio, and AA (4.5, "barely" within 10% above it) and AAA (7). The text that is painted is black or white, whichever reads better; the tinted candidates are for comparison.

## Alternatives considered

- A slide-over `Sheet` for the editor: it covers the list instead of moving it, cannot be a URL a person lands on, and has no route to go back through.
- A form library (superforms, formsnap): built around form actions and Zod, and this site is a browser talking to the API directly. The class is about a hundred lines and the résumé forms (lists inside lists) need the same state.
- Tailwind's `@theme static` for the palette: all of the theme's variables or none, and redefining the colors changes every other use of them.
- A class map (`bg-emerald-200` spelled out for every color): 26 families, 11 weights, and a dark variant of each, to keep in step with a migration.

## Consequences

- A page of this kind is a layout (`ListPane` with its list), a page with the form, and the pieces above. The first user is tags; each part's comment lists who uses it, and a page that adopts one adds itself.
- `mise web:palette` is rerun when Tailwind is upgraded, and a test compares the families with the database domain.
- Tests: pure logic in Bun (`bun test`), and the page's behavior (the slide and the back button, the dirty guard, the validation count and focus, the picker, slug history, a stale save, delete) in Playwright's `journey.test.ts`, since they need the signed-in account.

# Testing

## C#

- xUnit v3 on Microsoft.Testing.Platform. Tests sit beside the code as `Foo.Tests.cs` in the same project and namespace ([ADR 0023](../../docs/adr/0023-api-feature-folders-and-colocated-tests.md)). `mise test:missing` lists source files with no sibling test.
- The class is `FooTests`, and a test is named `Member_Behavior` (`Create_DuplicateSlug_ReturnsUnprocessable`).
- Anything that touches data is an integration test against the dev database, with no mocks. Pure helpers (string extensions, attributes, the SQL memoizer) get plain unit tests with no database. Use data no other test shares (`test-{Guid.NewGuid():N}` slugs) and delete what you insert in a `finally`, passing `CancellationToken.None` so cleanup runs even when the test was canceled.
- Tests connect as the DML-only `josholson_api` role, like the API, so a missing grant fails here. `mise db:provision` creates it; rerun it after a migration adds a schema. API tests never need the owner, and `ApiRoleTests` checks the role cannot change structure. The one exception is the tests of the scoped databases' own machinery (`Common/Db/ScopedDatabase*`), which make empty `seed_test_<id>` databases as the owner through `ScopedDatabaseTestData` (`TestDatabase.OwnerConnectionString`) and drop them when the test ends. The exception is the seed tool's tests (`JoshOlson.Database`: seeding, migrating, the lock): they build, read, and change databases and write tables the API role may not, so they connect as the owner through `DatabaseEnvironment.OwnerConnectionString()`. Roll back what they insert, or work in a database or schema of their own.
- The seed tool's tests are slow where they repeat work on the server, so they share it. Two tests with the same arrange and act are one test with both sets of assertions, named for the scenario (`Foo_Bar_BazAndQux`, not one test for `Baz` and one for `Qux`). A starting point that takes real work to reach (runs of `seeds:migrate`) is built once per test run and stamped into each test's own directory, so a test pays for the one run it is about and still has files nobody else changes (`FooScenarios`, `FakeSeedRepository.StartAtAsync`). A shared starting point is built with `CancellationToken.None`, so a canceled test does not leave a canceled task for the others. The reasons are in [ADR 0040 (the seed tool's tests share scenarios and databases)](../../docs/adr/0040-seed-tool-tests-share-scenarios-and-databases.md).
- A seed tool test never asserts a count, color, slug, or ID of the real seed layers, which grow with the site. Which fixture to reach for (real names, a reference): `SampleLayers` for a test with no server; `FixtureSeeds` for layers over the real schema (counts from `RootRows`, `ChildRows`, and `Tree`); `SeedWorkspace` for a repository of the test's own; `FakeSeedRepository` and `FooScenarios` for `seeds:migrate` over the small schema; `ScratchDatabase` for a database of the test's own; `SeedTestServer` for everything shared (the database operations, the container tools, the real template and tool); `SeedAppRunner` for the command line. A migration or layer a test writes has fixed text, so its template stays on the server, unless the test asserts that a template was built.
- A test class takes what it needs in its constructor ([ADR 0032, constructor injection in tests](../../docs/adr/0032-constructor-injection-in-tests.md)). `Common/Testing/Startup.Tests.cs` builds the container from the API's own registrations, and each test gets its own scope, so the open connection, every `*Service` and `*Repository`, and every `*TestData` helper arrive fresh. Never build a connection, repository, or service by hand in a test. Constructor only: xUnit cannot inject into a test method's parameters, so a `[Theory]` takes its data as arguments.
- Take the token once, in a field: `private readonly CancellationToken _cancellationToken = TestContext.Current.CancellationToken;`.
- Time is `FakeClock` (`Common/Testing`). `Startup` registers it as the scoped `IClock`, so a test takes `FakeClock clock`, calls `clock.Advance(...)`, and the services in its scope see the new time. It starts at the current time rounded down to the microsecond, which is what Postgres keeps, so a time that makes the round trip compares equal.
- Controller tests take an `HttpClient` for the API in memory (and a `WebApplicationFactory<Program>` if they need the factory). Both are scoped and start on first use. `NpgsqlDataSource` is there for a test that needs a second connection, and it reads and writes NodaTime types like the API's.
- A helper that creates and removes a feature's rows is a sealed class named `*TestData` (`AuthTestData`), registered as scoped by `Startup`.
- Helper types go inside the test class. The convention scan skips nested types, so a fake named `FooService` there is not registered by `ConventionRegistration`.
- A test that needs the database fails with a message if `POSTGRES_API_PASSWORD` is not in the environment or `.env`. Start and provision the dev database first (see CLAUDE.md).

## TypeScript and Playwright

- Unit tests are `*.test.ts` beside the code, run by `bun test` (`mise web:test:unit`), and a test builds what it needs in the test (a fake `fetch` for the API client). The generators in `web/scripts` are tested the same way.
- Playwright tests are in `web/tests` and run against a production build with a real API: `web/tests/support/api.ts` makes a scoped database from the `minimal` layer and runs the API on it, and `mise seed:clean` drops the database afterward. That API starts with a setup secret of its own and no account, so setup is open: a test that needs a signed-in account sets up through the page with that secret (`e2e()` in `tests/support/environment.ts`). Never point them at the dev database.
- A passkey is a Chromium virtual authenticator over CDP (`addVirtualAuthenticator` in `tests/support/webauthn.ts`), so no key is touched and no real credential is made. Chromium only. A real key is a manual check (`mise passkey`). A browser refuses to make a second passkey on an authenticator that already holds one for the site, so a test that adds a passkey adds a second authenticator and has the first stay silent (`respond(false)`) while the second makes it. The first must answer the confirmation and the second must not: an authenticator that answers "no such passkey" ends the request before the one that has it can, so the test silences the second and answers with the first, while it holds the confirmation options request (`page.route`) so the page cannot ask in between. Racing the page is what made this test flaky.
- One worker, for now: the run's one API is fixed to one database, so every test shares it. This is a stopgap, not the design. [ADR 0033 (a scoped database per test)](../../docs/adr/0033-scoped-databases-per-test.md) has each test clone its own database and send a scope ID in a header, which the API resolves to that database (Playwright sets it on the browser context, and the web server forwards it), and that header is not built yet; when it is, the tests can run in parallel and the journey can be split, with the account and its passkey in a seed layer. Until then the account is one, and setup closes with its first passkey, so `journey.test.ts` is the one file that sets up and enrolls (the other files, which run before it, see a site that has no passkey yet), and the one where a test that needs a signed-in account goes (the tags page's, after the passkeys'). Its tests run in order on one browser (`test.describe.configure({ mode: 'serial' })`), because each depends on the passkeys the one before left. Other files stay independent of it and of each other, and never enroll.
- Watch with `mise web:test:headed` or `mise web:test:ui`.
